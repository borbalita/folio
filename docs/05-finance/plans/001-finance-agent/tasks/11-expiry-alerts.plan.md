# 001/11 — Expiry alerts and Reconnect all Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The owner is warned in Finance and by email before bank access expires, and renews every expiring or expired bank in one sitting.

**Architecture:**
- Two new `bank_connections` columns:
  - `invalidated_at`: set when Enable Banking says the session is gone.
  - `expiry_notice`: the last email stage sent.
- A pure `connection_status(valid_until, invalidated_at, now)` gives `active`, `expiring` or `expired`.
- The bank sync decides which emails are due (`14d`, `3d`, `expired`, once each) and sends them through Yahoo SMTP. It marks a connection invalid on a session error and keeps syncing the others.
- Reconnecting clears both columns. Accounts are matched by `identification_hash`, then by IBAN, so their ids, and the transactions linked to them, stay.
- The frontend shows a warning in Finance. Reconnect all queues the banks in `sessionStorage` and runs each consent in turn through the callback page.

**Tech Stack:** FastAPI, SQLAlchemy + Alembic, stdlib `smtplib` and `email.message`, React + TS. No new dependencies.

**Spec:** [../README.md](../README.md) (Design → Failure modes), task [11-expiry-alerts.md](11-expiry-alerts.md).

## Global Constraints

- Statuses:
  - `expired`: `invalidated_at` is set, or `valid_until <= now`, or there is no session.
  - `expiring`: `valid_until - now <= 14 days`.
  - `active`: everything else.
- Session-invalid error codes, read from the `error` field of Enable Banking's JSON body: `EXPIRED_SESSION`, `CLOSED_SESSION`, `REVOKED_SESSION`, `SESSION_DOES_NOT_EXIST`. `ASPSP_ERROR` is not one of them; it is ambiguous (see 001/08's Verified notes).
- Email stages in order: `14d` (at most 14 days left), `3d` (at most 3 days left), `expired`. Send the highest stage that is due when it is higher than the stored `expiry_notice`, and send only that one. Store the stage only after the send succeeds.
- Email:
  - From and to `YAHOO_EMAIL`, logged in with `YAHOO_APP_PASSWORD`, through `smtp.mail.yahoo.com:465` (SSL).
  - Subject: `Folio: {bank} bank access expires in {n} days`, or `Folio: {bank} bank access has expired`.
  - Body: one sentence and the accounts page link. No transaction data.
  - Link: `ENABLE_BANKING_REDIRECT_URL` with its trailing `/callback` removed.
  - Missing Yahoo settings: log `expiry_notice_skipped` and continue. The sync doesn't fail.
- A failed email send is logged (bank and stage only) and retried on the next run. It doesn't fail the sync.
- Reconnect (`complete_connection`): set `invalidated_at = None` and `expiry_notice = None`. Match each new account to an existing row of the same connection by `identification_hash`, then by IBAN, and update that row in place.
- The migration is autogenerated after 001/06 merges (its `0cb48528ec95` is already applied to the dev database). Applying it needs the owner's OK.
- Logs carry the bank, stage and status only.

## Review Focus

1. **A sync runs every 8 hours, and the 14-day mark falls between runs.** The next run at 13.6 days still sends `14d`, because stages are "due at or below", not "exactly at". (Task 2 test.)
2. **A connection first seen at 2 days left** gets only the `3d` email, not `14d` as well. (Task 2 test.)
3. **SMTP is down.** The sync still stores transactions, and the stage isn't recorded, so the next run retries. (Task 2 test.)
4. **Reconnect all is cancelled at the bank halfway.** The queue is cleared, and the callback shows the error and the link back. A later Reconnect all starts again from what is still expiring or expired. (Task 4: manual.)
5. **Enable Banking returns a new `identification_hash` for the same IBAN on reconnect.** The existing account row is updated rather than duplicated, so transactions stay linked. (Task 3 test.)

### Task 4: Warning and Reconnect all (frontend)

**Files:** `frontend/src/lib/api.ts` (`status` on `BankConnection`), `frontend/src/lib/reconnect.ts` (new: a `sessionStorage` queue with try/catch), `frontend/src/pages/finance/FinanceLayout.tsx` (warning banner), `frontend/src/pages/finance/AccountsPage.tsx` (per-bank status and the Reconnect all button), `frontend/src/pages/finance/BankCallbackPage.tsx` (continue the queue)

- Banner text: `{bank} bank access expires in {n} days.` or `{bank} bank access has expired.`, with a link to Accounts. It shows when any bank is expiring or expired.
- Reconnect all shows only when a bank is expiring or expired. It queues those banks in BANKS order and starts the first one. On success, the callback page starts the next bank in the queue, or goes to Accounts when the queue is empty. On an error, it clears the queue.
