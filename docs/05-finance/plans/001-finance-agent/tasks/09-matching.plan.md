# 001/09 — Invoices matched to transactions: implementation plan

Task: [09-matching.md](09-matching.md). Spec: [README](../README.md), Decisions → "A strong match marks an invoice paid automatically".

**Goal:** open invoices link to the debits that paid them, automatically when the match is strong, as owner-confirmed suggestions otherwise.

## Design

- **Pure rules** in `app/finance/matching.py`, over plain dataclasses so the acceptance tests need no database:
  - `InvoiceFacts` (id, amount, currency, iban, invoice number, reference, payee, start date) and `Debit` (id, booking date, positive outflow, currency, counterparty IBAN and name, remittance).
  - Window: booked on or after the invoice date (the email's sent date when the invoice has none) and at most 120 days later.
  - Signals: `amount` (equal amount and currency, required), `iban` (equal after normalising), `reference` (the invoice number or reference, alphanumerics only, 4+ characters, found in the remittance text the same way), `name` (a shared payee/counterparty token of 4+ characters, ignoring legal-form and country words).
  - `propose(invoice, debits, rejected, taken)`: one strong candidate (amount and iban or reference) → `linked`; several strong → each `suggested`; otherwise every amount+name candidate → `suggested`. Rejected pairs and debits already linked to another invoice are skipped.
- **Table `invoice_matches`** (RLS): invoice, transaction (both cascade), status `linked` / `suggested` / `rejected`, source `auto` / `owner`, signals, timestamps. Unique per pair; partial unique indexes allow one `linked` row per invoice and per transaction.
- **Persisting** in `app/database/matches.py`:
  - `match_for_user(user_id)`: the owner's open invoices with an amount, and their unlinked debits; applies the proposals. A linked proposal marks the invoice paid with `paid_by = "match"`. Suggestions are upserted; rejected rows are never touched.
  - `confirm(match_id)`: linked, source owner, invoice paid; the invoice's other suggestions go.
  - `reject(match_id)`: rejected; if it was the link, the invoice returns to open (re-checked).
  - Un-marking a paid invoice by hand rejects its link, so matching doesn't link it again.
- **Triggers:** after each email ingest run (manual and scheduled), at the end of a bank sync (counts `linked` and `suggested`), and after an invoice edit.
- **API:** invoices carry `match` (the link: id, source, date, counterparty, amount, bank) and `suggestions`. `POST /finance/matches/{id}/confirm` and `/reject`, owner-only and scoped like invoices.
- **UI:** a "Matched automatically" label in the list; on the invoice page, a payment section with the linked transaction and **Not this payment**, and suggestions with **Confirm** and **Reject**.

## Steps

1. Red: `tests/finance/test_matching.py` for the five `(test)` criteria on `propose`, plus window, reference and name edge cases. Green: `matching.py`.
2. Model, autogenerated migration with RLS added by hand; RLS test passes.
3. `matches.py` with mock-session tests (link marks paid; confirm; reject of a link reopens; unmark rejects the link).
4. Triggers in ingest run, bank sync, invoice edit, with tests.
5. API routes and invoice payloads, with route tests.
6. Frontend: types, list label, payment section; `pnpm tsc --noEmit`, `pnpm lint`.
7. Owner approves `alembic upgrade head`; browser check of undo; owner's 90-day spot check.
